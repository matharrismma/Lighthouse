The honest architecture

You cannot run an AI on a LoRa node — a Meshtastic/RNode board is a microcontroller, and the link carries bytes, not models. So we don't pretend to. Instead:

The radio carries the mesh. A small computer behind it runs the engine. A mesh peer sends a question; your station answers in a compact, verifiable reply. No internet. No provider. No cloud.

  • The node (ESP32 / nRF52 + LoRa) — relays the mesh, carries tiny signed artifacts.
  • + a companion (a Raspberry Pi, an old phone, a mini-PC; solar-capable) — runs the deterministic engine offline: verify, and answer from the keeping.
  • + ~8 GB RAM — adds a small local model for drafting, still with no internet.

We chose Reticulum (RNS) over plain Meshtastic text: it's a full encrypted networking stack over the same radios, with real request/response — and its identity layer cryptographically proves an answer came from your station.

Stand up a station

1

Get the engine on your companion computer

Clone the repository onto the Pi / phone / mini-PC that sits behind the radio. The engine is Python, standard-library at its core.

2

Try the brain with no radio at all

Prove the round-trip first — this needs no hardware:

python -m api.reticulum_bridge --simulate "the love of God"
python -m api.reticulum_bridge --simulate "is 17 a prime number"

The first returns a verified card from the keeping with a pull-ref; the second is routed to the verifier rather than guessed at.

3

Add Reticulum + your LoRa radio

Install Reticulum and configure an RNodeInterface for your LoRa board in ~/.reticulum/config (see the Reticulum manual for your radio + region).

pip install rns
# configure your RNode interface in ~/.reticulum/config, then:
python -m api.reticulum_bridge --identity ~/.nh_station_id

Your station announces itself on the mesh and answers /ask requests. --no-draft runs it in pure-lookup mode (verified content only). radio transport: field-test pending

4

Optional — offline drafting with a small local model

For answers beyond the keeping, add a local model. No internet, no API key, no cost:

curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen2.5:3b

The station prefers verified content; it only drafts when the keeping has nothing, and every draft is marked (draft) on the wire so no one mistakes it for verified truth.

Verified bulletins — the part that matters in a crisis

A relief volunteer's node receives: "Water point open at the school gym, north entrance." It came through three relays nobody vetted. Did one of them change "north" to "south"? She runs the verifier — offline, no signal — and sees: unaltered, authentic, signed by the relief net's key. She trusts it. Had a relay flipped a word, she'd see it was altered, and ignore it.

Publish a signed, content-addressed bulletin. The full bundle travels by Reticulum, SD card, or hand-to-hand; the one-packet seal-ref (~68 bytes) fits a single LoRa message.

python -m api.bulletin --publish "Water point open at the school gym, north entrance. Boil 1 min."

Any recipient confirms it with no server and no internet — supply the seal-ref to check it wasn't altered, and the issuer's pinned public key to confirm who signed it:

python -m api.bulletin --verify bulletin.json --ref nh1:<hash> --pubkey <issuer-key>

Two layers, and we never claim more than we provide: unaltered needs no key (recompute the hash); authentic needs the issuer's pinned key. A bundle carrying its own key only proves it's internally consistent — trust comes from a key you pinned out-of-band. tested offline
